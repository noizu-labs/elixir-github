# Generation & Decode Hierarchy

How `mix github.gen` turns `docs/github-api/api.github.com.json` into the typed
client surface, and how each emitted module decodes a response.

## Generator pipeline

`Mix.Tasks.Github.Gen.run/1`:

1. **Load spec** — read the vendored OpenAPI JSON (`@spec_path`).
2. **Build context** — collect object schemas and shared parameters; compute
   which schemas are "structable" (object types with properties) and map each to
   a module name (`Noizu.Github.<CamelizedKey>`).
3. **Clean output** — wipe the previous `lib/api/` tree so stale files don't
   linger.
4. **Emit structs** — one module per structable schema with a permissive
   `from_json/2`.
5. **Emit collections** — a typed wrapper (`Noizu.Github.Collection.<Item>`) per
   schema that appears as an array item, plus the generic
   `Noizu.Github.Collection` and the `Noizu.Github.Raw` passthrough.
6. **Emit category modules** — group operations by tag into
   `Noizu.Github.Api.<Category>`, one function per operation.

Every emitted file carries the "Generated by `mix github.gen` … Do not edit by
hand" banner.

## Response model resolution (`classify_schema`)

For each operation the generator inspects the first present success status
(`200`→`201`→`202`→`203`→`204`) and its `application/json` schema, then:

| Response schema shape | Emitted model |
|-----------------------|---------------|
| `$ref` to a structable schema | `Noizu.Github.<Schema>` |
| `$ref` to a non-structable / inline schema | `Noizu.Github.Raw` |
| `array` of `$ref` to structable item | `Noizu.Github.Collection.<Item>` |
| `array` of inline/unknown items | `Noizu.Github.Collection` (generic) |
| no schema / no JSON content (e.g. `204`) | `Noizu.Github.Raw` |

The chosen model atom is baked into the generated `api_call/5` call, so runtime
dispatch is a single `apply(model, :from_json, [json, headers])`.

## Struct decode conventions

Each `Noizu.Github.<Schema>` defines `defstruct` over the schema's properties and
a permissive `from_json/2`:

- `from_json(nil, _)` → `nil`; `from_json(list, _)` → maps each element (so a
  struct used as an array item still works).
- Fields are read with `Map.get`, never pattern-matched — **extra and missing
  keys are tolerated**. This is what makes the client robust to spec drift.
- Nested `$ref`s decode recursively (`NullableSimpleUser.from_json(...)`, etc.);
  arrays of refs map over the item decoder.
- The catch-all `from_json(other, _)` returns `other` unchanged, so an
  unexpected shape never crashes.

## Collection wrappers

`Noizu.Github.Collection.<Item>` wraps `items` decoded via the item struct and
normalizes three body shapes into `%{items, total, complete, links}`:

- bare array → `total = length(list)`, `complete = true`
- search envelope `%{items, total_count, incomplete_results}` →
  `total = total_count`, `complete = !incomplete_results`
- anything else → passed through as `items`

`links` is always `Noizu.Github.extract_links(headers)`. The generic
`Noizu.Github.Collection` does the same without typing its items.

## Fallbacks

`Noizu.Github.Raw` is the catch-all model: it stashes the decoded body in
`:data` and pagination links in `:links`, and is used for inline objects, unions,
and empty bodies. Together with `Collection`, it guarantees **every endpoint
returns a value with `:links`**, even when the OpenAPI schema is ambiguous or
absent.

## Regeneration contract

- Generated code lives only under `lib/api/` and is wiped before each run.
- Hand-written code (`noizu_github.ex`, `application.ex`, `format.ex`, the mix
  task itself) lives outside `lib/api/` and is never touched by generation.
- `test/gen/generator_test.exs` guards the generator's output shape.
